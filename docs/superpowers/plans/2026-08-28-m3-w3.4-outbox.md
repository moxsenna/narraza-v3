## PM ratifications (frozen for W3.4)

1. R1 has no external production channel; the production handler registry is **empty**.
2. Never register a fake/no-op handler that would consume existing events.
3. No `OUTBOX_ENABLED` flag. The consumer is a maintenance module, independent of `JOB_PROCESSOR_ENABLED` (same status as retention). An empty registry idles without consuming.
4. No automatic `uncertain -> dead` promotion, and no arbitrary max-attempt retry policy.
5. First `deliveryGeneration = 0`; dead replay creates `previous + 1`. First claim `attemptCount = 1`.
6. Expired `processing` lease is reclaimed at the **same** generation with `attemptCount += 1`.
7. `completed` / `uncertain` / `dead` are terminal for that generation. Only `dead` is replayable in W3.4.
8. Handler execution happens **outside** the DB transaction: Tx Claim -> COMMIT -> handler -> Tx Finalize -> COMMIT.
9. `attemptCount` is the claim/finalization fence; a stale claimant performs zero mutation.
10. Stable handler idempotency key `outbox:${consumerKey}:${event.dedupeKey}`, unchanged across attempts and replay generations.
11. `OUTBOX_LEASE_SECONDS` default 60. Lease eligibility and all operational timestamps come from the PostgreSQL clock; poll/idle timers stay Node-scheduled.
12. Embedded consumer uses `DATABASE_URL_OUTBOX` (least privilege, S6.3), never `DATABASE_URL_WORKER`, and never receives provider keys.
13. Zero schema changes, zero migrations. Existing receipt schema (status CHECK, lifecycle CHECK, generation >= 0, unique `(outbox_event_id, consumer_key, delivery_generation)`) is authoritative.

## State machine

```text
no receipt
    | claim
    v
processing generation=0 attemptCount=1
    |-- handler completed ------------> completed
    |-- handler uncertain(errorCode) -> uncertain
    |-- handler dead(errorCode) ------> dead
    \-- handler/process throws
          -> receipt stays processing
             lease expires
             claim SAME generation, attemptCount += 1

dead generation=N
    | explicit replayDead()
    v
processing generation=N+1 attemptCount=1
```

Unhandled exceptions are never silently classified as `dead` or `uncertain`.

## Claim eligibility

Deterministic oldest-first by `occurred_at` then `id`, restricted to event types registered for that consumer, in a short READ COMMITTED transaction using `FOR UPDATE ... SKIP LOCKED`.

- Case A — no receipt: create generation 0, `processing`, `attemptCount=1`, `processing_started_at` and `lease_expires_at` from PG clock.
- Case B — latest receipt `processing` with expired lease: reclaim the same receipt/generation, `attempt_count += 1`, refresh `processing_started_at`/`lease_expires_at`.
- Case C — latest receipt `completed`/`uncertain`/`dead`: not claimable automatically. `dead` only via explicit `replayDead`.

## Finalization fence

Requires exact `outboxEventId` + `consumerKey` + `deliveryGeneration` + `attemptCount`, status still `processing`, lease still live. Terminal rows never return to `processing`. `uncertain`/`dead` require a non-empty `lastErrorCode`; `completed` clears it.

## Operational settings

`OUTBOX_POLL_MS=1000`, `OUTBOX_IDLE_BACKOFF_MS=5000`, `OUTBOX_LEASE_SECONDS=60`, `OUTBOX_SHUTDOWN_DRAIN_MS=30000`. No heartbeat in W3.4.

## Deployment

R1 stays two PM2 processes (`web`, `worker`). `apps/worker-outbox` becomes a real entrypoint composing the **same** consumer module and DB adapter as the embedded worker-gen module; the state machine is never duplicated across apps.

## Out of scope

W3.5 UI, M4 workflow/prompt/routing, AI provider implementation, frontend, S8.6 alert sweeper, schema/migration changes.
