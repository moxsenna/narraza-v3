# M3 W3.2 Workflow Invocation Three-Phase Attempt Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add durable `WorkflowInvocation`/`GenerationAttempt` lifecycles, first-billable-success PostgreSQL winner CAS, attempt-bound `AiUsageEvent` facts, and three-phase application harness while preserving W3.1 publication fencing and disabled production worker.

**Architecture:** Tx A authorizes exact live job owner and creates/reuses deterministic invocation/attempt IDs. Injected non-throwing executor runs outside UoW; Tx B finalizes attempt, records usage, and selects first eligible billable success; only fresh winner receives CPU validation outside UoW. Tx C reuses `JobService.withFencedPublish` and existing `appendSentinel` solely as transactional publication evidence.

**Tech Stack:** TypeScript 5.9, Node.js 22, pnpm 11.9, Vitest 4.1, Prisma 7.9, `pg` 8.22, PostgreSQL 16/Testcontainers 12.0.

## Problem, Users, Business Goal, Scope

### Problem summary

Concurrent workers and retries can finish same logical stage. System needs durable attempts, one billable-success winner, complete incurred usage facts, and stale-owner publication denial without holding DB transactions across external work.

### Target users

- Writers needing no duplicate/stale generation publication.
- Operations/finance needing durable usage facts after cancellation, lease loss, or tombstone.
- Engineers needing provider-neutral phase boundaries before M4/M5.

### Business goals

- Prevent zombie/duplicate publication.
- Preserve billable external-result facts.
- Keep cancellation/deletion reliable.
- Establish deterministic application seam without activating worker/provider.

### Main journey

1. Caller supplies deterministic invocation/attempt IDs plus live lease identity.
2. Tx A locks project, authorizes exact live job, creates/reuses running invocation, locks invocation, creates started attempt, commits.
3. Fresh attempt only: injected executor runs outside UoW and returns normalized billable success/failure plus usage.
4. Tx B finalizes attempt and appends/replays one attempt-bound usage fact. Successful result selects winner only after current authorization checks.
5. Fresh selected winner receives CPU validation outside UoW. Validation failure leaves immutable winner but blocks Tx C.
6. Tx C locks project then applies W3.1 fenced job checks, appends exact sentinel, terminalizes job, commits atomically.
7. Expected stale/cancel/tombstone/late outcomes retain attempt+usage but do not validate/publish.

### Required / optional / out of scope

**Required:** corrected status vocabulary, Tx A authorization, deterministic ID/replay semantics, rollback controls, null-winner CAS, precedence, immutable billable winner, tombstone lock protocol, exact sentinel, normalized executor states, retry evidence, PostgreSQL concurrency.

**Optional:** metadata-only logs through existing seams. No analytics infrastructure.

**Out of scope:** schema/migration, worker rewrite, production activation, W3.3 financial engine, M4 provider recovery/pricing, M5 validation fallback/domain publication, UI.

## Frozen Contracts

```ts
type WorkflowInvocationStatus =
  | 'queued' | 'running' | 'succeeded' | 'failed' | 'cancelled';
type GenerationAttemptStatus =
  | 'started' | 'succeeded' | 'failed' | 'cancelled';
type FinalizableAttemptStatus = 'succeeded' | 'failed';

interface BeginAttemptInput extends JobLeaseIdentity {
  readonly invocationId: string;
  readonly attemptId: string;
  readonly stageKey: string;
  readonly schemaVersion: number;
  readonly payload: JsonObject;
}

type BeginAttemptResult =
  | { readonly kind: 'started'; readonly invocation: WorkflowInvocationRecord; readonly attempt: GenerationAttemptRecord }
  | { readonly kind: 'already_started'; readonly invocation: WorkflowInvocationRecord; readonly attempt: GenerationAttemptRecord }
  | { readonly kind: 'conflict' }
  | { readonly kind: 'not_authorized' };

interface UsageMetrics {
  readonly priceSnapshotId: string;
  readonly inputTokens: number;
  readonly outputTokens: number;
  readonly providerCostMicroIdr: bigint;
}

interface FinalizeAttemptInput extends JobLeaseIdentity {
  readonly invocationId: string;
  readonly attemptId: string;
  readonly status: FinalizableAttemptStatus;
  readonly providerRequestId: string | null;
  readonly resultHash: string | null;
  readonly schemaVersion: number;
  readonly payload: JsonObject;
  readonly usage: UsageMetrics;
}

type WinnerOutcome =
  | 'selected'
  | 'selected_replay'
  | 'already_won_by_other'
  | 'ineligible_owner'
  | 'cancelled'
  | 'project_tombstoned'
  | 'attempt_failed';

type FinalizeAttemptResult =
  | { readonly kind: 'finalized'; readonly attempt: GenerationAttemptRecord; readonly winner: WinnerOutcome }
  | { readonly kind: 'replayed'; readonly attempt: GenerationAttemptRecord; readonly winner: WinnerOutcome }
  | { readonly kind: 'conflict' }
  | { readonly kind: 'not_authorized' };

type ExecutorOutcome =
  | { readonly kind: 'billable'; readonly status: FinalizableAttemptStatus; readonly providerRequestId: string | null; readonly resultHash: string | null; readonly schemaVersion: number; readonly payload: JsonObject; readonly usage: UsageMetrics }
  | { readonly kind: 'recoverable_no_response'; readonly reason: 'rejected' | 'aborted' | 'threw'; readonly errorCode: string };
```

Executor contract is non-throwing at harness boundary: harness catches reject/throw/abort and normalizes to `recoverable_no_response`. It never invents usage.

### Begin semantic tuple

Exact replay tuple is `(projectId, jobId, invocationId, stageKey, attemptId, schemaVersion, payload-jsonb)`. Lease token, fence version, and lease expiry are authorization inputs, not persisted begin semantics. Renewed valid lease replay with same ownership token/fence and later expiry may return `already_started`; changed semantic tuple returns conflict. A reclaimed lease with changed token/fence is unauthorized even when tuple matches.

### Finalize semantic tuple

Exact terminal replay tuple is locked attempt identity plus `(status,providerRequestId,resultHash,schemaVersion,payload-jsonb)` and caller-supplied usage metrics `(priceSnapshotId,inputTokens,outputTokens,providerCostMicroIdr)`. W3.2 derives persisted `chargedParty` as literal `system`; replay compares stored `chargedParty` against derived `system`. DB timestamps and generated `AiUsageEvent.id` are excluded.

### Exact Tx C sentinel

```ts
context.appendSentinel({
  aggregateType: 'workflow_invocation',
  aggregateId: invocationId,
  eventType: 'workflow_attempt_validated',
  dedupeKey: `workflow-attempt-validated:${invocationId}:${attemptId}`,
  schemaVersion: 1,
  payload: {
    projectId,
    jobId,
    invocationId,
    attemptId,
    stageKey,
    resultHash,
  },
});
```

Payload contains identifiers/hash only, no provider body or validated domain content. Existing `OutboxPort.append` performs plain insert; duplicate dedupe throws unique violation and Tx C rolls back. W3.2 does not claim semantic replay for sentinel.

### Task 4: Attempt-Bound Usage and Complete Replay Controls

**Files:** create usage adapter; modify workflow integration/unit tests and TxPorts composition.

**Interfaces:** consumes locked attempt record and `UsageMetrics`; produces immutable insert/replay/conflict.

#### Replay control table

| Attempt state | Attempt tuple | Usage row | Usage tuple | Result | Writes/commit |
|---|---|---|---|---|---|
| `started` | incoming finalize | missing | n/a | finalize + insert usage | commit |
| `started` | incoming finalize | matching preexisting | matching | finalize + usage replay | commit |
| `started` | incoming finalize | preexisting | divergent | `conflict` | rollback attempt finalize |
| terminal | matching | missing | n/a | insert missing usage, then read-only winner classification | commit |
| terminal | matching | present | matching | `replayed`, read-only winner classification | commit, no mutation except none |
| terminal | matching | present | divergent | `conflict` | rollback/no writes |
| terminal | divergent | any | any | `conflict` | rollback/no writes |
| missing/cross-project attempt | n/a | any | any | `not_authorized` | no writes/no existence leak |

“Read-only winner classification” never updates invocation. If matching terminal attempt is current winner, return `selected_replay`; if another winner exists, return `already_won_by_other`; if no winner, return eligibility classification without rerunning null-winner CAS. This prevents replay from changing historical selection.

### Validation meaning

Winner is first billable successful external result, not first CPU-valid result. Tx B fixes winner before CPU validation by PM lock. CPU validation failure leaves winner immutable, blocks sentinel/job success, and returns validation-failed outcome. W3.2 does not start fallback. M5 owns validation repair/fallback orchestration.

## Transaction and Retry Diagram

```text
Logical Tx A (UoW may retry callback with stable invocationId/attemptId)
  lock project FOR UPDATE; require deletedAt null
  lock exact live job owner; require running/live/no cancel/token/fence
  create/reuse running invocation; lock invocation
  create started attempt or return already_started
COMMIT

Outside UoW, fresh started only
  executor exactly once per harness call
  normalized billable result + UsageMetrics OR recoverable_no_response

Logical Tx B for billable result (UoW may retry callback with stable IDs)
  finalize attempt

COMMIT expected denials; rollback semantic conflicts/DB error attempts

Outside UoW, fresh selected only

  failure leaves immutable winner, no Tx C
```

## CAS SQL Strategy

- Existing unique `(jobId,stageKey)` enforces invocation identity.
- Existing unique `(invocationId,ordinal)` plus invocation row lock serializes zero-based allocation.
- Attempt CAS only updates `status='started'`.
- Usage unique `dedupe_key` supports immutable insert-or-compare.
- Winner CAS only updates `status='running' AND winner_attempt_id IS NULL`; no invocation fence mutation.
- Authorization locks occur before winner read/classification, preventing leakage.
- Project-first lock order applies Tx A, Tx B eligibility, Tx C, and tombstone writer protocol.
- PostgreSQL clocks drive timestamps and lease checks.
