# M3 W3.3 Credit Engine Implementation Plan

> **Status:** Planning and architecture review only. Production implementation is blocked until PM ratifies Gate 1 and Gate 2 in this document.
>
> **For implementation agents after ratification:** use `superpowers:subagent-driven-development` or `superpowers:executing-plans`; complete one task and its review gate at a time.

**Goal:** Build append-only, idempotent user-credit accounting around quotes, reservations, jobs, usable output, failed-job zero charge, late-attempt reconciliation, credit summaries, and quote/bundle retention without changing W3.2 provider-usage facts or activating production AI processing.

**Architecture:** Keep provider accounting and user accounting separate. `AIUsageEvent` remains immutable attempt-bound provider-cost evidence. User balance changes only through append-only `credit_ledger`; held value comes from `credit_reservations`. Quote confirmation atomically consumes one owner-bound quote, creates one open reservation, and creates/enqueues one reciprocally bound job. Job terminalization classifies durable usable output, settles or releases only safe amounts, and places unresolved financial outcomes in `closing`. Late attempts append usage first, then reconcile reservation in a separate UoW. PostgreSQL row locks, CAS predicates, deterministic keys, and durable result links provide concurrency safety and replay.

**Tech stack:** TypeScript 5.9 strict, Node.js 22, pnpm 11.9, Vitest 4.1, Prisma 7.9, `@prisma/adapter-pg`, PostgreSQL 16/Testcontainers.

## 3. Ratification Gate 1 — `AIUsageEvent` and User Settlement

### 3.1 Source-fixed facts

- W3.2 writes exactly one logical usage event per finalized attempt with `dedupeKey = usage:{attemptId}`.
- Adapter derives project/job/attempt identity from locked attempt.
- Persisted `chargedParty` is literal `system`.
- Exact duplicate returns replay; divergent duplicate returns conflict.
- Late, losing, failed, cancelled, stale-owner, and tombstoned billable attempts retain provider usage.
- W3.2 performs no reservation or user-ledger mutation.
- D4 requires zero user charge when no candidate/artifact is durably published.
- Provider cost and user-ledger settlement are separate accounting domains.

### 3.2 Recommended interpretation for PM ratification

Ratify:

> `AIUsageEvent` records immutable provider usage and provider-facing cost. `chargedParty='system'` means Narraza incurred provider liability when usage occurred; it does not determine final user-ledger settlement. W3.3 never updates or replaces this event. User settlement is a separate append-only ledger fact derived from immutable usage, durable usable-output evidence, and a frozen billing allocation policy.

Required behavior:

- Never mutate `AIUsageEvent.chargedParty` to `user`.
- Never append another usage event for same attempt to represent user settlement.
- Never replace `providerCostMicroIdr` with quote, reservation, retail price, subsidy, or user charge.
- Preserve exact W3.2 replay/conflict semantics.
- Provider billing corrections use future compensating evidence, not mutation of original usage.

### 3.3 Recommended successful-settlement policy

Recommended W3.3 policy:

```text
eligibleActualCost = sum(providerCostMicroIdr for policy-eligible contributing attempts)
userSettlement = min(eligibleActualCost, reservedMicroIdr)
release = reservedMicroIdr - userSettlement
systemSubsidy = max(eligibleActualCost - userSettlement, 0)
```

User never pays above confirmed reservation. Overage remains full provider-cost evidence, becomes system subsidy, and emits deterministic ops evidence.

**PM decision required:** define `policy-eligible contributing attempts`:

- **Recommended:** only attempts proven to contribute to durably published usable output. Losing, late, failed, cancelled, stale-owner, tombstoned, validator-rejected, and unpublished attempts remain system cost.
- Alternative: all billable attempts for successful job. Higher user charge; user bears retries/races outside user control.
- Alternative: fixed workflow retail amount. Requires explicit commercial price policy not present in current sources.

**PM decision required:** approve actual-cost-capped-at-reservation formula or supply another frozen commercial formula.

### 3.4 Required immutable billing-allocation evidence

Current schema cannot durably prove:

- contributing usage-event set;
- billing policy/version;
- why user settlement differs from provider cost;
- system subsidy/overage;
- usable-output classification basis.

Recommended additive model:

```prisma
model CreditBillingAllocation {
  id                         String
  projectId                  String?
  jobId                      String
  reservationId              String
  usableOutputKind           String
  usableOutputRef            String
  contributingAttemptIdsHash String
  providerCostMicroIdr       BigInt
  userSettlementMicroIdr     BigInt
  systemSubsidyMicroIdr      BigInt
  billingPolicyVersion       Int
  billingPolicyPayload       Json
  dedupeKey                  String   @unique
  createdAt                  DateTime
}
```

Exact naming may follow surrounding Prisma conventions, but semantics stay immutable. Add DB checks for nonnegative amounts, positive policy version, object payload, and conservation:

```text
systemSubsidy = max(providerCost - userSettlement, 0)
userSettlement <= reservation.reservedMicroIdr
```

Prefer tenant-safe FK/reference strategy only after retention audit. Do not introduce cascade that deletes financial evidence with project/job/attempt rows.

## 4. Ratification Gate 2 — Reservation Exposure and Closing

### 4.1 Frozen values and invariant

```text
R = reservedMicroIdr
S = settledMicroIdr
L = releasedMicroIdr
E = exposureMicroIdr
```

Always:

```text
R > 0
S >= 0
L >= 0
E >= 0
S + L + E = R
```

Existing PostgreSQL checks already enforce these amount invariants.

`R > 0` is non-negotiable and is not relaxed by W3.3. A reservation exists for both `user_paid` actions (user-confirmed, reduces user available/held) and for `system_funded` actions (upstream budget-created, does NOT reduce user balance). The two buckets share the same lifecycle CHECKs but differ in settlement policy (`S_target = max(commercialUserCharge, 0)` vs `S_target = 0`).

Exposure means reservation amount still held because final disposition cannot yet be proven. It is not provider cost already incurred.

### 4.2 State machine

| State | Financial shape | Meaning |
|---|---|---|
| `open` | `S=0, L=0, E=R`, `closingAt=null` | Job active or queued; entire hold unresolved |
| `closing` | `E>0`, `closingAt!=null` | Job terminal but relevant attempt/outcome remains unresolved |
| `settled` | `S>0, E=0, S+L=R`, `closingAt!=null` | Final usable output with positive user settlement |
| `released` | `S=0, L=R, E=0`, `closingAt!=null` | Final zero-charge non-cancellation outcome (user-paid S=0 OR system-funded full release) |
| `cancelled` | `S=0, L=R, E=0`, `closingAt!=null` | Final cancellation outcome |
| `expired` | `S=0, L=R, E=0`, `closingAt!=null` | Reservation expired before usable execution |

`closingAt` is part of the derived tuple, not a side effect of the status choice. Every terminal status requires `closing_at IS NOT NULL` (`prisma/migrations/20260722093000_credit_validation_publish_ops_expand/migration.sql:47-48`), so a direct `open -> settled` close must write `closingAt` in the same statement or the lifecycle check aborts the enclosing publish transaction. Every transition that leaves `open` writes:

```text
closingAt = COALESCE(closingAt, NOW())
```

matching the existing precedent at `packages/db/src/repos/ledger-port.ts:90-93`.

Successful usable output with calculated user settlement zero uses `released`, because existing DB check forbids `settled` with `S=0`.

Mirror rule: `closing` is legal **only** when `E_target > 0`, because the DB check requires `exposure_micro_idr > 0` for that status (`prisma/migrations/20260722093000_credit_validation_publish_ops_expand/migration.sql:46`). Whenever computed `E_target = 0` the reservation must go straight to the terminal status matching `S`, never to `closing` — even if a relevant attempt is still unresolved. See §4.4 G.

Both rules share one root cause: status is derived from the computed `(S, L, E)` tuple, never chosen first and reconciled after. Compute the tuple, then select the only status the DB accepts for it.

Never reopen financial terminal state. Never decrease persisted settlement or release.

### 4.3 Conservative exposure policy

Current schema has no immutable per-attempt or per-stage authorized exposure ceiling. Until M4 supplies real workflow-plan budgets, W3.3 must not invent partial exposure allocation.

Recommended W3.3 rule:

```text
S_target = min(max(commercialUserCharge, 0), R)
E_target = unresolvedRelevantAttempts > 0 ? R - S_target : 0
L_target = max(0, R - S_target - E_target)
safeRelease = max(0, L_target - L_current)
```

Preconditions:

```text
S_target >= S_current
L_target >= L_current
S_target + L_target <= R
```

Divergence produces typed reconciliation conflict plus idempotent ops evidence. Never overwrite prior facts.

Consequence: zero-output terminal job with unresolved attempt holds full reservation in `closing`. This is conservative but schema-valid and avoids unsafe release. Per-attempt partial exposure allocation is deferred until real M4 plan budgets exist.

### 4.4 Required transitions

A. Quote confirm:

```text
new reservation: open, S=0, L=0, E=R
```

B. Queued job:

```text
reservation remains open
```

C. Attempt starts or finishes while job active:

```text
reservation remains open; usage is separate
```

D. Multiple successful attempts:

```text
winner/contributing output policy determines settlement eligibility;
non-contributors remain system usage
```

E. Terminal usable output, no unresolved attempt:

```text
S=S_target, L=R-S, E=0
closingAt = COALESCE(closingAt, NOW())
status=settled when S>0, else released
```

F. Terminal zero output, no unresolved attempt:

```text
S=0, L=R, E=0
closingAt = COALESCE(closingAt, NOW())
status=released or cancelled by terminal reason
```

G. Terminal job with unresolved relevant attempt:

Compute the tuple first, then derive status. Never assume `closing`.

```text
S = S_target
L = L_current + safeRelease
E = R - S - L
closingAt = COALESCE(closingAt, NOW())   -- required for closing AND for every terminal status

if E > 0   -> status=closing
if E == 0  -> status=settled  when S > 0
              status=released when S == 0
```

The `E = 0` branch is reachable and must be handled: when the user charge reaches the reservation cap, `S_target = R`, so `E_target = 0` even with attempts still unresolved. Writing `closing` there violates the DB check `status='closing' AND exposure_micro_idr > 0` and would abort the enclosing publish transaction, destroying the durable output along with the financial close.

Terminalizing at `E = 0` while attempts remain unresolved is safe because user charge is already capped at `R`: any later attempt can only produce a zero-delta replay, which transition I already treats as a no-op.

H. Late attempt result:

```text
Tx B commits attempt + immutable usage first;
separate reconciliation UoW recomputes unresolved count and safeRelease
```

I. Final close:

```text
last unresolved attempt resolved;
E=0;
append only settlement/release deltas;
status settled/released/cancelled/expired
```

J. Queued cancellation:

```text
preserve W3.1 job-first lock;
full release;
dedupe release:{reservationId}:queued-cancel;
status=cancelled
```

K. Running cancellation:

```text
request cancellation only; no early release;
terminal reconciliation enters closing or cancelled
```

L. Execution retry on same job:

```text
reservation stays open; attempt history retained
```

M. Manual retry:

```text
new job requires new quote/reservation;
old reservation reconciles first and is never reused
```

## 5. Ledger and Summary Semantics

Use current persisted vocabulary; do not reintroduce stale docs names:

```text
charge
refund
grant
adjustment
reservation_settlement
release
```

W3.3 reservation lifecycle uses:

```text
reservation_settlement  debit
release                 credit
```

No `reserve` ledger row. Reservation hold exists in `credit_reservations`.

### 5.1 Book and hold formulas

Freeze query semantics:

```text
bookMicroIdr =
  grants
  + refunds
  + credit adjustments
  - charges
  - reservation settlements
  - debit adjustments
```

`release` is excluded from book balance. It reduces held amount through reservation state; including it in book would double-credit because reserve never debited book.

```text
heldMicroIdr = Σ(E) for open reservations
reconcilingMicroIdr = Σ(E) for closing reservations
availableMicroIdr = bookMicroIdr - heldMicroIdr - reconcilingMicroIdr
```

For compatibility with source prose saying held includes closing, internal total hold is:

```text
totalHeldMicroIdr = heldMicroIdr + reconcilingMicroIdr
```

Returned view:

```ts
interface CreditSummaryView {
  available: bigint;
  held: bigint;
  reconciling: bigint;
}
```

Values are credits after conversion. Compute all micro-IDR aggregates from one transaction snapshot, then convert:

```text
available credits: floor(max(availableMicroIdr, 0) / MICRO_IDR_PER_CREDIT)
held credits: ceil(heldMicroIdr / MICRO_IDR_PER_CREDIT)
reconciling credits: ceil(reconcilingMicroIdr / MICRO_IDR_PER_CREDIT)
quote credits: ceil(maxAmountMicroIdr / MICRO_IDR_PER_CREDIT)
book display: floor(bookMicroIdr / MICRO_IDR_PER_CREDIT)
```

Integer arithmetic only:

```ts
floor = amount / unit;
ceil = amount === 0n ? 0n : (amount + unit - 1n) / unit;
```

Use single server constant `MICRO_IDR_PER_CREDIT = 10_000_000n`. Reject negative inputs at conversion boundary except explicitly signed adjustment aggregation before final nonnegative available policy.

## 6. Quote and Confirmation Contract

### 6.1 Quote issuance

Scope note: §6.1–§6.3 describe the **paid-action path only** (D4 "Berbayar"). Free actions (D4 "Gratis") never enter this path; see §6.4.

Input binds:

```text
userId
projectId
workflowPlanId | null
workflowPlanHash
bundleId | null
dependencyHash
maxAmountMicroIdr
issuanceRequestId
```

Rules:

- validate authenticated owner without enumeration;
- validate 64-character lowercase hashes;
- validate `maxAmountMicroIdr > 0` (strictly positive, not merely nonnegative);
- use PostgreSQL time;
- `expiresAt = dbNow + 10 minutes` by default;
- deterministic issuance replay by `issuanceRequestId` returns exact quote only when semantic tuple matches;
- divergent replay returns typed conflict;
- quote issuance does not reserve credit or create job.

Zero-max rejection is a hard precondition, not a downstream failure. Rationale: existing DB check `reserved_micro_idr > 0` (`prisma/migrations/20260722093000_credit_validation_publish_ops_expand/migration.sql:35-38`) makes a `maxAmountMicroIdr = 0` quote structurally unconfirmable, so accepting one would persist a guaranteed-dead quote row. Reject with typed `invalid_quote_amount` before any insert.

`credit_quotes` currently persists `CHECK (max_amount_micro_idr >= 0)`. W3.3 tightens this in application code only; the DB check is **not** narrowed to `> 0`, because §6.4 may later persist system-funded quote rows and narrowing is not reversible without another migration. PM ratification item 11 records this asymmetry.

### 6.2 Confirmation

Input:

```text
userId
projectId
quoteId
confirmationRequestId
expectedWorkflowPlanHash
expectedDependencyHash
job input with deterministic jobId/reservationId
```

One `ReadCommitted` UoW:

1. serialize user balance with the single frozen primitive `SELECT id FROM users WHERE id = $1 FOR UPDATE`, taken before the project lock (no advisory-key alternative — two confirmations choosing different primitives would not interlock, leaving the overspend guarantee unfounded);
2. lock active project and validate owner;
3. lock quote by exact user/project/ID;
4. inspect durable confirmation replay link first;
5. reject expired quote using `clock_timestamp()`/DB operational time;
6. reject `quote.maxAmountMicroIdr <= 0` with typed `invalid_quote_amount`, before consume and before any reservation/job insert (defence in depth against legacy rows issued under the old `>= 0` rule);
7. compare workflow-plan and dependency hashes;
8. compute book and held from locked financial snapshot;
9. require `availableMicroIdr >= quote.maxAmountMicroIdr`;
10. consume quote once;
11. create open reservation with `R=E=maxAmount`, `S=L=0` (`R > 0` guaranteed by steps 6 and the issuance rule);
12. create queued job and reciprocally bind reservation;
13. persist confirmation request/result linkage;
14. commit.

Concurrent confirmations produce one reservation/job. Exact same `confirmationRequestId` returns same IDs. Different request ID against consumed quote returns already-consumed result without creating another reservation/job.

### 6.3 Required confirmation migration

Current `credit_quotes.request_id` cannot safely serve both issuance and confirmation, and no relation recovers result after commit.

Add:

- `credit_reservations.quote_id` nullable for legacy rows, required for new W3.3 confirmation path;
- unique FK/reference to `credit_quotes.id` with retention-safe delete behavior;
- `credit_reservations.confirmation_request_id` nullable with partial/global unique index;
- exact replay lookup through quote/reservation and existing reservation/job reciprocal binding.

Do not overload quote issuance `request_id` as confirmation request ID.

Add job integrity check if confirmed jobs may carry workflow plan:

```sql
CHECK (workflow_plan_id IS NULL OR bundle_id IS NOT NULL)
```

M4 still owns proving request-beats-snapshot and real plan binding.

### 6.4 D4 free-action path (system-funded reservation)

**PM RATIFICATION — D4 system-funded actions (amendment #12 required)**

The `system_funded` bucket is **NOT reservation-less**.

A D4-free action:
- requires no user-facing paid CreditQuote confirmation;
- creates **no user charge ledger entries**;
- **does not reduce user available/held credit**;
- **remains inside the reservation/budget pipeline as a system-funded reservation**;
- records incurred provider usage as system liability;
- may receive an internal auto-quote/frozen system budget when M4 supplies the actual workflow plan.

Rationale stated as PM decision rather than omission:

- D4's phrase "tetap melalui pipeline reservation" means a **system-funded reservation row**, not a zero-value paid reservation. It is conceptually different from `user_paid`: no user-credit hold exists; provider cost is absorbed as internal/system liability; reconciliation uses the same state machine but settles with `S=0, L=R` and never touches the user book balance.
- The `reserved_micro_idr > 0` guard stays intact; we do not relax it to allow zero-reservation paths. System-funded reservations carry strictly positive amounts derived from an internal budget/auto-quote mechanism wired at M4.
- W3.2 already writes exactly one `AIUsageEvent` per attempt with `chargedParty='system'` hardcoded by the adapter. For system-funded reservations, `AIUsageEvent` becomes the sole durable payment evidence; the reservation itself is released without ledger entry because no user settlement occurred.

**Free-action job admission (W3.3 boundary):**

- `GenerationJob.reservationId` points to an existing open system-funded reservation created upstream by the system-budget path (M4 wires the actual auto-quote/frozen budget artifact). Reservation must not reduce user available/held credit.
- W3.3 adds the *contract and guard*: a typed `ActionFundingModel = 'user_paid' | 'system_funded' | 'pre_d4_legacy'` resolved from job kind by an application-owned policy (three buckets — see §10), plus the invariant that `system_funded` jobs must reference an `open`, system-funded reservation (created via the budget path; user balance unchanged) and `user_paid` jobs must supply a non-null `reservationId` naming an `open`, still-unbound reservation at enqueue, which the adapter then binds reciprocally. Job kinds present at base are `pre_d4_legacy` and are exempt from the enqueue guard and the §9 incident path; they are **not** exempt from settlement.
- W3.3 does **not** implement fair-use counting (60/day/user). That is quota enforcement, not credit accounting; `docs/implementation-plan.md:87` places intake-reply mechanics in M4. W3.3 records the seam and asserts the credit-side invariants only.

**Settlement side:**

System-funded reservations **do** reach §4.4 transitions E/F/G, because these are real reservation rows subject to the same lifecycle CHECKs. Settlement computes `S_target = 0` (no commercial charge), leading to `L_target = R, E_target = 0`, status=`released` (or `cancelled`) with a full release but zero user-ledger rows. The `failed-job-zero-charge` guarantee still holds but now flows through the reservation state machine rather than bypassing it.

**Required tests (added to Task 4 and Task 11):**

- system-funded reservation created upstream with no user balance reduction;
- system-funded path job enqueues with non-null `reservationId` naming an open system-funded reservation;
- free-path attempt still writes exactly one `chargedParty='system'` usage event;
- `user_paid` job cannot enqueue with a null reservation;
- system-funded job **must** have a bound open reservation;
- system-funded terminal success and terminal failure both compute `S_target = 0`, transition to `released` or `cancelled`, run full release with zero ledger rows, and leave user book balance byte-identical to pre-run snapshot.

PM ratification item 12 covers this path. If PM instead wants a persisted zero-value system quote row for audit symmetry, that is a different design requiring a migration and must be ratified before Task 3, not retrofitted.

## 8. Transaction and Lock Order

Two disjoint lock families avoid forcing new quote rows into existing job lifecycle order.

### 8.1 Quote confirmation family

```text
users row            -- SELECT id FROM users WHERE id = $1 FOR UPDATE (frozen, sole primitive)
project
quote
new reservation insert
new job insert/bind
append-only rows
```

No existing job or existing reservation is locked during creation. Stable user serialization prevents two quotes from spending same available balance.

The `users` row lock is frozen as the only balance serialization primitive; no advisory-key variant is permitted. This ordering is already consistent with existing behaviour: `credit_reservations_user_id_fkey` (`prisma/migrations/20260722093000_credit_validation_publish_ops_expand/migration.sql:172`) takes `FOR KEY SHARE` on the same row during reservation insert, so user → project → quote introduces no inversion.

## 9. Transaction Boundaries

### Tx Q — quote issue

- owner/project validation;
- frozen scalar binding validation;
- DB expiry computation;
- insert/replay quote;
- no external work.

### Tx CFM — quote confirm, reserve, enqueue

- user balance serialization;
- project and quote locks;
- replay/expiry/hash/balance checks;
- quote consume;
- reservation/job creation and reciprocal bind;
- no external work.

### Tx A — attempt begin

- project;
- exact live job owner;
- invocation;
- attempt insert/replay;
- reservation untouched.

### Provider execution

- outside UoW.

### Tx B — attempt finalize and usage

- corrected project/job/invocation/attempt order;
- attempt finalization;
- usage append/replay;
- winner classification;
- reservation untouched.

### CPU validation

- outside UoW.

### Funding-model branch — applies to Tx P, Tx F, and Tx L

Every terminal or reconciling transaction resolves the funding model from the locked job row before touching any financial row:

The legacy bucket is a **modifier on assertions**, not an arm of the reservation branch. The financial path is selected by `reservationId` alone:

```text
legacy = funding(job.kind) == pre_d4_legacy   -- suppresses assertions and incidents only

job.reservationId IS NULL      -> if !legacy assert system_funded
                                  (should not happen for legacy or paid; this is the error path)
                                  skip reservation lock, allocation, and all ledger appends
                                  commit publish/outbox/job-terminal only
job.reservationId IS NOT NULL  -> if legacy: no assertion, run full financial path
                                  if non-legacy: assert user_paid OR system_funded
                                  for either, compute targets (system-funded sets S_target=0),
                                  run the normal financial path (including zero-settlement releases)
```

A legacy-kind job with a bound reservation still settles and releases through §4.4 E/F/G (typically with `S=0, L=R` for system-funded jobs). Suppressing settlement for legacy kinds would strand those reservations `open` at `E=R` forever — and because the shared fixture default kind is `prose` (`packages/db/src/job/job-test-fixtures.ts:58`), it would also silently disable W3.3's own `reservation-exposure` and `failed-job-zero-charge` evidence. The exemption is narrow by construction: assertions and incidents only.

A non-legacy `user_paid` job found with a null reservation at terminalization is a typed incident with ops evidence, never a silent zero charge. A system-funded job always carries a valid reservation created upstream by the system-budget path; it never bypasses settlement/release computation. Its `S_target = 0`, so it transitions to `released`/`cancelled` with `L=R` but writes **no** user-ledger rows. This is the "zero-charge" guarantee, but realized *through* the reservation state machine rather than *by skipping it*.

This branch is mandatory because system-funded jobs carry reservations but require a distinct settlement policy (`S_target = 0`); without an explicit branch an implementer would invent an unratified rule for the system-funded release.

### Tx P — durable publish and usable settlement

- project lock;
- fenced job lock;
- durable product output callback;
- usable-output classifier;
- funding-model branch (above);
- reservation lock;
- allocation evidence;
- settlement/release ledger deltas;
- reservation state update;
- outbox append;
- job terminal transition;
- one atomic commit.

W3.2 sentinel-only callback classifies zero output for user charging.

### Tx F — non-publish terminal reconciliation

- project/job lock;
- funding-model branch; `system_funded` sets `S_target=0`, runs normal release path;
- reservation lock;
- read invocation/attempt facts after locks;
- zero-output or closing classification;
- append safe financial deltas (zero for system-funded);
- update reservation;
- commit.

### Tx L — late reconciliation

Runs after Tx B commit:

- project/job lock;
- funding-model branch; `system_funded` resolves `S_target=0`, zero-delta replay or full release if closing;
- reservation lock;
- count relevant unresolved attempts;
- recompute monotone targets;
- append only safe deltas (none for legacy/system-funded zero-charge);
- final-close when exposure reaches zero.

Financial reconciliation never requires live lease ownership.

### Tx R — retention sweep batch

- select eligible rows with `FOR UPDATE SKIP LOCKED`;
- delete only unused, unconsumed, unreferenced quote/bundle rows older than 24 hours by PostgreSQL `NOW()`;
- bounded batch;
- no financial/audit evidence deletion.

- user debit above confirmed reservation;
