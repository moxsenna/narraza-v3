### Approved ledger vocabulary compatibility boundary

Amended W3.1 application contract `entryType='release'`, `direction='credit'` supersedes the undocumented SQL literal `reservation_release`. Prisma models both fields as `String`, so no Prisma model change is needed. Current migration `20260722093000_credit_validation_publish_ops_expand` rejects `release` and permits `reservation_release` in named CHECK constraints. Resolve the mismatch with one forward migration after that historical migration; never edit the historical migration.

The forward migration must execute atomically and in this order:

1. Acquire PostgreSQL's required table lock through the constraint changes and data update; treat the migration as a compatibility deployment boundary because application writes using `release` cannot start before migration completion.
2. Drop both named constraints `credit_ledger_entry_type_check` and `credit_ledger_type_direction_check` so existing `reservation_release` rows can be renamed.
3. Backfill once with `UPDATE "credit_ledger" SET "entry_type" = 'release' WHERE "entry_type" = 'reservation_release'`.
4. Recreate `credit_ledger_entry_type_check` with exactly `charge`, `refund`, `grant`, `adjustment`, `reservation_settlement`, and `release`.
5. Recreate `credit_ledger_type_direction_check` preserving current direction behavior: `charge` and `reservation_settlement` are debit; `refund`, `grant`, and `release` are credit; `adjustment` may use either allowed direction.

After migration, `release`/`credit` is accepted, `release`/`debit` is rejected, old literal `reservation_release` is rejected, and all other vocabulary/direction behavior is unchanged. Existing development DB has zero ledger rows, but migration upgrade evidence must prove old rows rename safely for other environments. Adapter writes exact application vocabulary `release`; no dual-write, compatibility translation, or second domain type is allowed.

## Application contract and state-machine rules

### Existing persisted job shape

`GenerationJobStatus` is the exact union `queued | running | succeeded | failed | dead | cancelled`.

`GenerationJobRecord` mirrors existing Prisma fields without invented columns: `id`, `projectId`, `kind`, `status`, `priority`, `availableAt`, `leaseToken`, `leaseExpiresAt`, `fenceVersion`, `cancelRequestedAt`, `retryOfJobId`, `bundleId`, `workflowPlanId`, `reservationId`, `schemaVersion`, `payload`, `createdAt`, and `updatedAt`.

`JobLeaseIdentity` carries only ownership proof: `jobId`, `leaseToken`, and `fenceVersion`. Project-scoped operations also receive `projectId` separately or as part of their typed input. A stale identity must be unable to heartbeat, requeue, finish, cancel as owner, acquire fenced publish, or publish a sentinel.

Define discriminated unions for insert, claim, terminal transition, cancellation, reclaim, and manual retry. Each union must distinguish success from expected CAS/state outcomes without relying on thrown exceptions. Required outcome meanings:

- Insert: inserted record or duplicate/conflict.
- Claim: claimed live record with lease identity, or no eligible job.
- Heartbeat: extended live lease, or lost ownership.
- Requeue: queued with incremented fence, or lost ownership/not allowed.
- Terminal: terminalized with incremented fence, already terminal, lost ownership, cancellation required, or cancellation blocks success.
- Cancel: queued cancelled, running cancel requested, already requested, already terminal, or not found.
- Reclaim: expired job requeued, expired cancel-requested job cancelled, or no expired job.
- Manual retry: new queued job, source invalid/nonterminal, cross-project source, explicit reservation binding invalid, or duplicate/conflict.

Do not expose Prisma types from `packages/application`.

### Required `JobPort` surface

`JobPort` has these methods and no implicit single-active-job helper:

- `insert`
- `findById`
- `listActiveByProject`
- `lockForUpdate`
- `claimNext`
- `heartbeat`
- `requestRunningCancellation`
- `cancelQueued`
- `requeueRunning`
- `transitionQueuedToTerminal`
- `transitionRunningToTerminal`
- `reclaimNextExpired`
- `lockForFencedPublish`

Method contracts enforce project scope where relevant, exact lease token/fence matching on owner operations, PostgreSQL lease validity, legal source/target statuses, and row-count/CAS outcomes. `listActiveByProject` returns all `queued` and `running` jobs in stable query order; it never assumes cardinality one.

### Required `LedgerPort` surface

`LedgerPort` exposes only `releaseQueuedCancellation`. Input binds exact `projectId`, `jobId`, and `reservationId`; includes an allocated ledger entry ID; and fixes dedupe key to `release:{reservationId}:queued-cancel`. Required domain vocabulary is `entryType='release'`, `direction='credit'`. Operation locks and validates exact reservation binding, releases all reserved amount, sets settlement and exposure to zero, and uses database `NOW()` for `closingAt`. Broad financial behavior remains W3.3.

### Legal transition and ownership semantics

- Inserted job starts `queued`, has `fenceVersion=0`, has null lease fields and null cancellation request, and uses explicit availability/reservation bindings.
- Claim selects one eligible queued row by `availableAt ASC`, `priority DESC`, `createdAt ASC`, `id ASC`. Claim sets `running`, creates a fresh lease token, sets DB-computed expiry, and increments fence once.
- Heartbeat requires `running`, exact token/fence, `leaseExpiresAt > NOW()`, and no terminal mutation. It changes only lease expiry and normal `updatedAt`; fence stays unchanged.
- Execution retry requires live exact owner, no cancellation request, and target `queued`; it clears lease fields, applies DB-computed `availableAt`, and increments fence once.
- Running success requires live exact owner and `cancelRequestedAt IS NULL`. A cancel-requested job cannot publish or succeed.
- Running cancellation finish requires live exact owner and an existing cancellation request. It terminalizes `cancelled` and increments fence once.
- Running failure/dead terminal transitions require live exact owner, legal target, and exact token/fence. They increment fence once.
- `queued -> cancelled` does not increment fence. No queued transition may become `succeeded`, `failed`, or `dead` through cancellation APIs.
- Terminal jobs are immutable under all state operations.
- Reclaim locks one expired running job. Null cancellation request requeues and increments fence once. Existing cancellation request terminalizes cancelled and increments fence once.
- Fenced publication lock requires `running`, exact token/fence, `leaseExpiresAt > NOW()`, and `cancelRequestedAt IS NULL` while row is locked `FOR UPDATE` in publication transaction.

### Service boundaries

`createJobService` exposes `cancel`, `manualRetry`, `claim`, `heartbeat`, `requeue`, `finish`, `reclaimOne`, and `withFencedPublish`.

- Every state mutation executes in a UnitOfWork transaction.
- External provider/stage work always runs outside UnitOfWork.
- `withFencedPublish` callback receives only `FencedPublishContext`, not `TxPorts`, `UnitOfWork`, Prisma, or generic `OutboxPort`.
- `FencedPublishContext` exposes one sentinel append capability sufficient to append the existing outbox event used by W3.1 tests. Sentinel `occurredAt` comes from `ports.dbNow()` in the same transaction, never a Node clock. Service orders `lockForFencedPublish -> callback publication -> running terminal transition to succeeded -> commit`.
- Callback failure rolls back sentinel and job transition together.
- No code path calls a generic success transition after external work without rechecking fenced ownership in the same transaction.

### Locked worker environment and timing contract

Extend the existing `workerEnvSchema` and `loadWorkerEnv`; do not create a second worker settings parser. Preserve all existing names/defaults and add only the W3.1 lifecycle fields below.

| Environment name            | Default | Validation and runtime mapping                                                                                                                    |
| --------------------------- | ------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| `JOB_PROCESSOR_ENABLED`     | `false` | Strict env boolean: unset, `false`, or `0` maps to `false`; `true` or `1` maps to `true`; every other value is invalid                            |
| `JOB_LEASE_SECONDS`         | `60`    | Existing positive integer; composition maps to `leaseMs=60000`                                                                                    |
| `JOB_HEARTBEAT_SECONDS`     | `20`    | Existing positive integer; composition maps to `heartbeatMs=20000`; must be strictly less than `JOB_LEASE_SECONDS`                                |
| `JOB_RECLAIM_SWEEP_SECONDS` | `30`    | Existing positive integer; composition maps to `reclaimSweepMs=30000`                                                                             |
| `JOB_POLL_MS`               | `1000`  | Positive integer; direct `pollMs` value                                                                                                           |
| `JOB_ERROR_BACKOFF_MS`      | `5000`  | Positive integer; direct `errorBackoffMs` value; must be greater than or equal to `JOB_POLL_MS`                                                   |
| `JOB_SHUTDOWN_DRAIN_MS`     | `30000` | Positive integer; direct `shutdownDrainMs` value; PM2 worker `kill_timeout` is fixed at `35000`, strictly greater than default/configured `30000` |

`RETENTION_SWEEP_MINUTES=60`, `RETENTION_MAX_AGE_HOURS=24`, `OUTBOX_POLL_MS=1000`, and `OUTBOX_IDLE_BACKOFF_MS=5000` remain unchanged and are not wired into the W3.1 job loop.

Provider-key validation remains a production invariant and becomes conditional on processor activation. `NODE_ENV=production` plus `JOB_PROCESSOR_ENABLED=true` requires at least one non-empty `OPENROUTER_API_KEY` or `GEMINI_API_KEY`; processor-disabled production requires neither key. The existing production prohibition on `AI_ENABLE_MOCK=true` and non-production mock-without-provider behavior remain unchanged.

Processor-disabled composition passes no processor, never invokes `claim`, and still runs one-at-a-time reclaim scheduling plus SIGTERM/SIGINT shutdown.
